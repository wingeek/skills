# react-babylon-map: Harness 工程实践总结

## 概要

这是一个**AI驱动的技术分析项目**：在尚未编写任何代码之前，利用 Harness (Claude Code) 进行深度技术调研，生成了一份从 react-three-map (Three.js) 迁移到 react-babylon-map (Babylon.js) 的完整技术方案。本总结关注**如何利用 AI 进行高效的技术决策和方案规划**，而非具体的技术实现细节。

---

## A - Approach: AI协作模式

### 介入方式

这个项目展示了 **AI-First 规划模式**：
- **阶段**: 技术可行性分析阶段，在编码之前
- **目标**: 评估两个技术栈的能力差异，制定迁移策略
- **AI角色**: 技术分析师 + 架构师，而非代码实现者

### 提示策略分析

从 plan.md 的结构可以推断出有效的提示模式：

| 提示维度 | 示例 | 效果 |
|----------|------|------|
| **能力对比** | "对比 react-babylonjs 和 R3F 的能力" | 生成系统性的能力矩阵 |
| **场景映射** | "如何实现共享 WebGL 上下文？" | 触发深度技术分析 |
| **风险识别** | "这个方案有什么风险？" | 生成风险缓解表 |
| **API对照** | "Three.js API 对应到 Babylon.js 是什么？" | 生成迁移映射表 |

### 上下文提供策略

plan.md 展示了**结构化上下文**的价值：

```
有效上下文结构:
1. 源项目路径: C:\Users\neychang\workspace\react-three-map
2. 目标项目路径: C:\Users\neychang\workspace\react-babylon-map
3. 明确约束: 不改变对 maplibre-gl, react-map-gl 的依赖
4. 当前架构描述: 双渲染模式、相机同步机制
```

**经验**: 明确的项目路径和约束条件让 AI 能够更精准地理解任务边界。

## I - Insights: AI 揭示的分析

### 系统性能力评估

AI 生成了 react-babylonjs 的能力评估表，这是人工容易遗漏的：

| 能力类型 | 发现 |
|----------|------|
| **直接可用** | `useBeforeRender`, `useScene`, `useEngine`, Portal 支持 |
| **需扩展** | 外部 GL 上下文、手动渲染控制、相机输入隔离 |

**价值**: 这种"能力分类"思维帮助快速识别工作量和风险。

### 跨框架 API 对照表

AI 生成了详细的 Three.js → Babylon.js API 映射：

```
R3F                    →  react-babylonjs
─────────────────────────────────────────
useFrame(cb)           →  useBeforeRender(cb)
useThree(s => s.camera)→  useScene()?.activeCamera
createRoot(canvas)     →  <MapEngine externalContext={gl}>
advance(timestamp)     →  scene.render()
gl.resetState()        →  engine.resetCustomCache()
```

**价值**: 这种映射表大大降低了学习曲线，让迁移工作可以并行化。

### 矩阵存储差异的早期发现

AI 识别了一个容易被忽视的细节：
- MapLibre 使用**列主序**（OpenGL 约定）
- Babylon.js 使用**行主序**

这导致了专门的 `transposeMatrix()` 工具函数设计，避免了后续大量调试。

### 坐标系兼容性分析

AI 提前识别了坐标系问题并提供了解决方案：
```typescript
scene.useRightHandedSystem = true;  // 与 Three.js 一致
```

## P - Pain Points: AI 的局限

### 上下文缺失场景

| 缺失信息 | 影响 |
|----------|------|
| **实际代码库** | 无法验证假设，分析基于文档而非实际实现 |
| **性能基准** | 无法评估迁移后的性能差异 |
| **团队技能** | 无法评估学习曲线对团队的实际影响 |

### 需要多轮迭代的场景

1. **具体实现细节**: plan.md 中的代码片段是伪代码，实际实现需要更多迭代
2. **边界条件**: 错误处理、降级策略等需要实际编码时发现
3. **性能调优**: 渲染循环优化需要实测

### 幻觉风险点

- **API 存在性**: 部分 react-babylonjs API 可能不存在或签名不同
- **兼容性假设**: 假设的功能组合可能在实际中不兼容

**缓解策略**: 将 AI 生成的代码视为"伪代码"而非可直接使用的实现。

## R - Refinement: 流程优化

### 有效的提示模式

1. **约束前置**: 先说明"不改变什么"，再讨论"改变什么"
2. **结构化输出请求**: 明确要求表格、对照表、分阶段计划
3. **风险导向**: 主动询问"什么可能出错"

### 验证策略

plan.md 展示了良好的验证思维：
- 穷举单元测试（矩阵转换）
- 视觉回归测试（截图对比）
- Phase 验证检查点

### 平衡点

| 方面 | AI 擅长 | 人工必需 |
|------|---------|----------|
| 技术对比 | ✅ 系统性分析 | 领域经验判断 |
| API 映射 | ✅ 文档查询 | 实际可用性验证 |
| 风险识别 | ✅ 模式匹配 | 业务优先级判断 |
| 实现代码 | ⚠️ 伪代码级别 | 生产级质量 |

## C - Collaboration: 协作模式总结

### 信任与验证平衡

```
高信任区域（直接采用）:
- API 文档查询
- 技术概念解释
- 结构化对比分析

需要验证区域（伪代码对待）:
- 具体实现代码
- API 签名细节
- 兼容性假设
```

### 探索 vs 执行

| 阶段 | AI 角色 | 人工角色 |
|------|---------|----------|
| **探索** | 生成选项、对比分析 | 设定边界、做决策 |
| **规划** | 结构化方案、风险识别 | 评审、优先级排序 |
| **执行** | 代码生成、测试编写 | 代码审查、集成调试 |

### 知识沉淀模式

从 AI 对话中提取的知识应该：
1. **去上下文化**: 移除项目特定细节，保留通用模式
2. **结构化**: 转化为表格、检查清单、模板
3. **可检索**: 存储在 memory 或文档系统中

## T - Takeaways: 关键收获

### 可复用的提示模板

**技术迁移分析模板:**
```
我需要将 [项目A] 从 [技术栈X] 迁移到 [技术栈Y]。

约束条件:
- 保持 [不改变的部分]
- 需要改变 [明确要改变的部分]

请分析:
1. 能力对比矩阵（可直接用/需扩展/不可用）
2. API 映射表
3. 主要风险和缓解措施
4. 分阶段迁移计划
```

**技术选型分析模板:**
```
评估 [技术A] vs [技术B] 用于 [场景]。

评估维度:
- 核心能力匹配度
- 学习曲线
- 生态成熟度
- 与现有技术栈兼容性
- 长期维护成本

输出: 对比表格 + 推荐结论
```

### 工作流改进建议

1. **规划阶段**: 使用 AI 生成结构化分析，人工做决策
2. **文档化**: 将 AI 生成的分析保存为可评审的文档
3. **验证循环**: AI 生成 → 人工验证 → 反馈修正 → 最终确认

### 技能开发需求

基于这个项目，需要的 Harness 技能：
- `framework-migration-analyzer` - 框架迁移分析
- `api-mapping-generator` - API 对照表生成
- `risk-assessment-helper` - 风险评估辅助
